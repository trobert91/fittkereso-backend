# fittkereso-backend

## Code style

- Favor small, modular services with a single responsibility over large ones. Split classes when they start doing more than one job.
- Avoid code duplication — extract shared logic into a helper/service rather than copy-pasting between call sites.
- Prefer many small, readable classes over few large ones. Optimize for readability and maintainability.
- Use lodash extensively for array/object manipulation (`isUndefined`, `isEmpty`, `compact`, etc.) instead of hand-rolled equivalents — it's already a dependency and used throughout the codebase.

## Database / migrations

- Do **not** write TypeORM migration files for now. The dev config (`apps/api/src/config/config.yaml`) has `sync: true`, so schema changes apply automatically via TypeORM's `synchronize`.
- Once the current phase of development settles, we'll generate one consolidated migration capturing the schema at that point — don't generate incremental ones per change in the meantime.
- **The public website reads these tables directly** (`../fittkereso-frontend`, read-only role `fittkereso_web`): `product_model`, `brand`, `product_category`, `product_image`, `offer`, `seller`, and the enums `offer_condition_enum` / `offer_availability_enum`. Its mirror of the columns it reads is `fittkereso-frontend/src/db/schema/catalog.ts`. Renaming or dropping one of those columns breaks the site: change the mirror in the same piece of work (its `contract.test.ts` names the mismatch). The site's URLs identify products by `product_model.publicId` (`p<publicId>`, e.g. the comparison's; it survives a rename, a slug does not): a random, unused 9-digit number, so they can't be walked through. A trigger assigns it on insert and another refuses to change it (`ProductPublicId1793000000000`); code never sets it. It also repeats two rules: `offers.json` `freshnessDays` (its `OFFER_FRESHNESS_DAYS`) and `productDisplayName`. Its listing pages read a copy of each category's `filterSpecs`, `displayedSpecsInList`, `offerLevelSpecs` and the matching `jsonSchema.json` labels and units (`fittkereso-frontend/src/config/category-specs/*.json`): after changing those, run `npm run sync:category-specs` in the frontend (its `category-specs.test.ts` fails until then). The same applies to a category's `recommender.json` (the site's guided product finder: question steps and what each answer means in specs; nothing in this repo reads it at runtime). The site reads a resolved copy (`fittkereso-frontend/src/config/recommenders/*.json`, written by the same sync), and `recommender-config.spec.ts` checks the file against `recommender.schema.json` and the category's `jsonSchema.json`, so renaming a spec or an enum value it names fails that spec.
- **The site's search reads `product_model."searchName"` and `"searchVector"`, which only the database writes.**
  - The `product_model_search` trigger rebuilds both when `model`, `brandId`, `orderedSpecs` or `description` change, and `brand_search` refreshes a brand's products on a rename.
  - The functions are `search_normalize`, `search_prefix_query` and `product_search_vector`; the site calls the first two in its queries. They are in `libs/config/src/lib/migrations/1792000000000-product-search.ts` (`PRODUCT_SEARCH_SQL`).
  - The entity declares both columns `select/insert/update: false`, and their GIN indexes `synchronize: false`.
  - **A build without them that boots with `sync: true` drops the columns and their indexes.** Product writes keep working: the trigger skips missing columns. But the indexes only come back by re-running the migration's SQL.
  - The site's test DB applies a copy (`fittkereso-frontend/scripts/sql/search.sql`), and its contract test compares the functions. Change both together.
- **The partner portal in the same site writes two tables** (role `fittkereso_partner`): `app_user` and `seller_membership` (it also reads `seller`), mirrored in `fittkereso-frontend/src/db/schema/identity.ts`. The same mirror rule applies. It also repeats the account rules of `libs/user`: emails stored lower-cased, `app_user.role` / `passwordChangeRequired` as the authority mirrored into Supabase `app_metadata { role, password_change_required }`, the hold cleared only by set-password, a compensating Supabase delete when the local write fails, and at least one shop admin per seller. Change both sides together.
- **The site also writes `offer_click`** (role `fittkereso_click`, SELECT + INSERT on that table only): its `/api/v1/out/{offerId}` redirect logs every "go to shop" click there, and the partner portal reads the shop's click statistics from it. Mirror: `fittkereso-frontend/src/db/schema/clicks.ts`. The billing rule (one billable click per visitor, seller and product per 24 hours) lives in the site; this side only erases the visitor keys (`OfferClickRetentionService`, hourly, `offers.json` `clicks.visitorKeyRetentionHours`, which must stay at least the site's billing window).
- **The site also writes `finder_visitor` and `finder_result`** (role `fittkereso_finder`, SELECT + INSERT + UPDATE + DELETE on those two only): a visitor saving a guided-finder result is a `finder_visitor` row (only the SHA-256 of the key in its cookie) with named `finder_result` rows (the canonical answer string; `activatedAt` set while active, at most two active per category - the site's rule). Mirror: `fittkereso-frontend/src/db/schema/finder.ts`. This side only deletes visitors not seen for `finder.json` `retentionDays` (`FinderRetentionService`, nightly; the site's privacy notice states the period).
- Whenever a query needs a field or relation name as a string (`relations: [...]`, `order: {...}`, `select`, etc.), use `nameOf<Entity>('field')` from `@fittkereso-backend/utils` instead of a hardcoded string literal, so renames stay type-checked. For nested/dotted paths, build them as `` `relation.${nameOf<RelationEntity>('field')}` ``.

## Debugging & operational inspection

- Use **Loki** at `http://localhost:3100` as the primary source for debugging running-app behavior — task/pipeline progress, warnings, errors, model calls, cost, resolution decisions, stuck/failed import tasks. Query with `query_range` (not `query`). Processing traces are also stored in Loki; query them with `log_type="processing_trace"` for trace-level detail.
- Use the **fittkereso MCP server** (`http://localhost:8090/mcp`) for structured inspection and mutation of entities — products, categories, sellers, product sources, import tasks, brands — and for one-off actions (`enqueue_product_import_task`, `create_seller`, `update_product_source`, `update_product_source_category` for one category section of a source config, etc.) instead of writing/running ad hoc scripts. It's the preferred way to create or modify rows during manual testing.
  - If the MCP server's tools aren't showing up as available (e.g. `ToolSearch` finds nothing for it), don't assume the server is down — it may just not be wired into the current session. Verify with a raw HTTP probe first: `curl -s -X POST http://localhost:8090/mcp -H "Content-Type: application/json" -H "Accept: application/json, text/event-stream" -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'`. If that returns a real tool list, call tools directly over HTTP the same way (`method: "tools/call"`, `params: {name, arguments}`) rather than falling back to scripts.
  - When an argument contains non-ASCII characters (Hungarian diacritics, etc.) or heavy escaping (regex patterns), write the JSON-RPC payload to a file with the `Write` tool first and send it via `curl --data-binary @<file>` — inline shell heredocs mangle escaping/encoding.
  - Treat MCP and Loki as complementary, not either/or: MCP for "what does this row look like / make this change happen," Loki for "why did this run behave the way it did." When an import task or pipeline step looks stuck or failed via MCP, check Loki next rather than guessing or re-polling blindly.
